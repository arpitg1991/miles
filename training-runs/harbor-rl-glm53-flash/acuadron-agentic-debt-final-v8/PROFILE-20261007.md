## Why it is slow

The trainer is idle 58-82% of each step. The gym side cannot finish 64 variable-reward groups fast enough.

1. **Whole-group completion.** A group returns only after all eight attempts finish. Agent time per checkpoint has median 243 s, p90 1,033 s, p99 3,140 s (3,029 checkpoints sampled on 40 workers). The slowest attempt gates each group.
2. **Zero-variance waste.** Dynamic sampling examined 94, 86, 77, and 82 groups to keep 64 each time. 83 groups (23%) were dropped, 18 all-perfect and 9 all-zero in logged reasons.
3. **Engine load is low.** Engine decode medians: 21-24 running requests, about 1,650-1,850 tok/s per engine. The 48 engines are not saturated; the loop is bound by group completion, not GPU throughput.
4. **Long chains.** Mean tokens per episode grew from 66k to 167k across rollouts 0-3 as longer chains completed.
5. **Verifier is not the bottleneck.** Verifier phase median 21 s, p90 35 s, p99 125 s.

## Failures found

1. **Two workers reject every no-network task.** Harbor probes Docker kernel support once per worker process with a 30 s timeout and caches the result for the process lifetime. On `gym-6dbb6b7f78-h2rz6` and `gym-6dbb6b7f78-z2mfz`, the first probe ran 41 s during Docker warm-up, so the cached answer is "unsupported". Every later task fails with `network_mode='no-network' is not supported by EnvironmentType.DOCKER`. These two workers consumed 27 groups (216 attempts) without producing one trajectory. A manual `docker run --network none` on the same pod succeeds, so the kernel does support the mode; only the cached probe result is wrong. Fix options: restart the two gym-worker containers (each then re-probes), or raise the probe timeout upstream. No fix applied; a restart interrupts nothing on those workers because they produce nothing.
2. **Docker OOM kills still occur at 192Gi.** Eight gyms had a Docker sidecar OOMKilled since launch (was 30 in 6 h on v7 at 64Gi). 60 collect-hook `service "main" is not running` events and 14 `no_reward` drops followed. The new limit helps but does not remove the failure; eight concurrent trials can still exceed 192Gi.
3. **No disk evictions.** The 300Gi volume plus cleanup sidecar held; no `dind-storage` evictions and no cleanup threshold events in the sampled logs.
4. 45 engines logged `post-warmup freeze_gc failed` (a connection refused to port 15000 at warm-up). Health checks pass and generation works; no evidence this costs throughput.
